# 自我升级

## 为什么这一节必须存在

这个 skill 的每一次使用都会产出新知识：一条新签名、一个被推翻的阈值、一个解析 bug、一条够格晋升的
gate。**如果这些不写回文件，它们只存在于那一次会话的叙事流里，下次归零。**

那正是本 skill 用来诊断别人的病：**知识进了叙事流、没进物证流**。
不实现自我升级，这个 skill 就得了它自己诊断的病。

它也是晋升梯作用在自己身上的结果——skill 自身就是"复发 ≥3 次且有稳定操作序列"的产物。

## 分发层 vs 本地层（首次使用必读）

**基线、不满句式、洪水画像都是环境属性，不是通用常数。**
p50=10 次压缩、`view_image` 占 87% 输出——这些描述的是某一个人的语料。
换一个不用 subagent、不看图、说另一种语言的用户，分布完全不同。
拿别人的基线读自己的会话，**正是本 skill 要检测的 B 类裂缝：引用了一个在当前语境下不成立的东西。**

```
随 skill 分发（所有人相同）
  SKILL.md / references/*.md 的方法论部分 / scripts/*.py

本地校准产物（每人不同，绝不随 skill 分发）
  <skill>/local/
    baseline.json            本人语料的指标分位 + 本环境的工具输出画像
    dissat_candidates.jsonl  从本人历史挖出的不满句式候选（待人工确认）
    patterns.json            确认后的句式库
    gates.md                 本人项目的失效边
    falsified.md             本人推翻过的阈值
```

首次使用先跑校准：

```bash
python3 "$SESSION_FORENSICS_DIR/scripts/calibrate.py" \
  ~/.codex/sessions ~/.claude/projects
```

之后语料每增长一批就重跑一次。**指标只有相对本人基线的分位才有意义**——
绝对值（"failure_rate 0.33"）不可解释，分位（"你语料里的 p88"）才可解释。

⚠️ `references/signatures.md` 里出现的所有具体数字都带来源语料标注，
它们是**示例，不是常数**。读别人的 skill 文档时同理：先问"这个数字是谁的语料"。

## 每次使用后必答的四问

读完任何一个会话，在给出结论**之前**回答：

1. **出现新的洪水源 / 新签名了吗？** —— `flood_tool` 是否是表里没有的工具？是否有基线未覆盖的模式？
2. **有阈值被反例推翻吗？** —— 本次观测是否落在"应该命中却没命中"或"不该命中却命中"的位置？
3. **数字看起来不合理吗？** —— 不合理优先怀疑解析 bug，而不是怀疑会话。
   （实测教训：`patches=1370 / files=1066` 的怪比例，实际是正则吞掉了补丁体。）
4. **有东西跨会话复发第 2 次吗？** —— 是则晋升为 gate，不要等第 3 次。

## 写入路由（写错地方等于没写）

| 发现类型 | 写到哪 |
|---|---|
| 新签名、新基线、新洪水源 | `references/signatures.md` |
| 阈值被推翻 | `signatures.md` §已证伪 —— **只增不删** |
| 够格的 gate | `signatures.md` §gate 清单 |
| 平台字段 / 记录格式 | `references/<platform>-jsonl.md`、`references/platforms.md` |
| 脚本 bug | 改代码 **且** 在 `signatures.md` §解析陷阱留痕，附修复前后数字对比 |
| 心智模型变更 | `mental-model.md` —— 最保守，见下方门槛 |
| handoff 模板缺陷 | `references/handoff-packet.md` §实战修订记录 |
| 使用流程 / 禁止事项 | `SKILL.md` |

## 纪律

- **每条新增必须带实测数字 + 来源会话 id。** 禁止"通常""可能""一般来说"。
  没有数字的观察写进"未证伪的假设"，不写进签名表。
- **只增不删已证伪条目。** 它们是防止重犯的唯一机制。删掉一条被推翻的阈值，
  三个月后一定会有人（包括你自己）重新提出它。
- **n=1 标记为「单例观察」，不得写成结论。** n≥2 才能晋升 gate。
- **心智模型层的改动需要 ≥2 个独立 case**，且必须说明它解释了旧模型解释不了的什么。
- **任何归一化 / 分类器的验收必须同时过 ≥2 个会话，且规模差 ≥100×。**
  实证（2026-07）：`top_shapes` 的命令归一化在 `019f9a28`（2.6 MB）上验收通过，
  接到 `019f7843`（946 MB）上前 8 名有 5 条是 Codex JS 外壳——**只认 `cmd:"..."` 一种形态，
  漏掉 `{"cmd":"..."}`（键带引号）和 `tools.apply_patch(patch)` / `tools.write_stdin(...)`。**
  修好后两个会话前 8 名外壳噪声均为 0，并且 `js:apply_patch` 624× 让"用 exec 内嵌补丁"
  这条 gate 的违反次数**第一次变得可数**。单会话校准的归一化默认是过拟合的。
- **结论有边界就写边界，不要直接覆盖。**
  实例：早先"地板抬升不是杀手"在 18 次压缩下成立、60 次压缩下不成立 → 正确做法是补上适用区间
  （"~20 次内可忽略，>~40 次成为主要约束"），而不是把旧结论删掉。

## 对自己做审计（每次实质性修改后）

skill 自身也是会话产物，同一张签名表对它有效：

- **仪器分叉** —— 脚本是否在多处存在副本？
  实测已发生一次：`scratchpad/session_metrics.py`(307 行) 与
  `~/.claude/skills/session-forensics/scripts/session_metrics.py`(473 行) 并存，
  scratchpad 副本落后 166 行。处置：删除非权威副本，只保留 skill 目录下这一份。
  **草稿目录写脚本 → 稿件转正后必须删除草稿**，这是本 skill 自己的一条 gate。
- **定义分叉** —— 同一术语（如"探针/装配"、"A 类/B 类"）在 SKILL.md 与 references 中是否已漂移？
- **无证宣称** —— 文档里是否有没挂实测数字的断言？
- **上下文洪水** —— 单个 reference 文件是否大到每次加载都吃掉大量预算？超过约 200 行就该拆。

## 版本留痕

不维护版本号。**留痕靠「已证伪」表和「解析陷阱」表**——它们记录的是变化本身，
比版本号更有用：版本号只说"变了"，这两张表说"为什么变、变之前错在哪"。
